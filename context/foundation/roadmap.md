# Roadmap: 10xMedia

> Derived from `context/foundation/prd.md` (v1) + auto-researched codebase baseline.
> Edit-in-place; archive when superseded.
> Slices below are listed in dependency order. The "At a glance" table is the index.

## Vision recap

Watching YouTube videos is time-consuming — when regularly following informational and educational channels, the list of potentially interesting content grows faster than the available time. Existing tools summarize single videos but don't help choose WHICH video is even worth watching. 10xMedia turns a video (after pasting a URL and selecting the channel character: informational or educational) into a Polish-language summary on the basis of which the user decides whether to watch or skip it.

## North star

**S-01: user generates and saves a video summary** — the smallest end-to-end flow that proves the product's core (YouTube transcript → Polish summary tailored to the channel character) works. With the "speed" goal, this is the only slice that must land to validate the PRD's single success criterion (75% of summaries "good enough").

> "North star" here means the smallest end-to-end flow whose successful delivery proves the product's core hypothesis — placed as early as dependencies allow, because everything else only matters if this works.

### S-07: Summary generation telemetry (latency, cost, transcript)

- **Outcome:** (observability) every saved summary records how long generation took and what it cost on **both** paid providers — OpenRouter in dollars, Supadata in credits/API calls — and the transcript it was generated from is kept, so models, characters and transcript branches can be compared on speed, spend and input size — not just on content.
- **Change ID:** persist-time-and-cost (renamed from `summary-generation-telemetry` when the change folder was opened 2026-07-28)
- **PRD refs:** — (no direct PRD ref; carries F-02 impl-review findings F4 and F5, and feeds the PRD's Open Q2 "75% good-enough" tracking mechanism)
- **Prerequisites:** S-01. T4 (Supadata spend) additionally assumes S-08 is live — it is, deployed 2026-07-26 — because the second Supadata call and `videos.duration_seconds` both come from there.
- **Parallel with:** S-02, S-03
- **Blockers:** —
- **Unknowns:**
  - Single wall-clock `generation_ms` vs. split `transcript_ms` / `llm_ms`? — Owner: implementation. Block: no. (Split is more diagnostic given the 33 s vs. 254 s spread came from the *transcript* branch, not the LLM.)
  - Persist token counts alongside `cost_usd`, or cost only? — Owner: implementation. Block: no.
  - Reuse a stored transcript on re-generation, or always re-fetch? — Owner: user. Block: no. (Reuse saves Supadata cost and closes S-01's accepted double-fetch, but serves a stale transcript if the video's captions later change. A `fetched_at` column keeps the option of a staleness window open without deciding now.)
  - Retention: keep transcripts indefinitely, or purge after N days? — Owner: user. Block: no. (Indefinite is simplest and matches MVP scale; the erasure path is already covered — see Scope notes.)
  - **Supadata spend: record it per *summary*, or per *generation attempt*?** — Owner: user. Block: no. (Columns on `summaries` follow F4/F5 exactly and are near-free, but they are written only when a summary is persisted — so a 422 `transcript-unavailable` (1 billable credit), a refused/errored generation and the metadata retry's second credit all stay invisible, and those are precisely the wasted spend. An append-only `supadata_calls` ledger row per call catches all of it. Recommendation: ship columns first, note the blind spot, promote to a ledger only if the numbers stop adding up against `GET /v1/me`.)
  - **Derive credits from the price table, or read the vendor's own counter?** — Owner: implementation. Block: no. (Supadata returns no per-request cost in its response — unlike OpenRouter's `usage.cost` — so cost is either computed locally from the documented table or observed via `GET /v1/me`'s `usedCredits`, which is **free to call**. The counter is ground truth but org-wide, so concurrent generations interleave and a delta can be mis-attributed. Recommendation: count calls locally as the record of truth per row, and take a `usedCredits` reading as calibration, not as the per-row value.)
- **Risk:** Low risk — additive nullable columns on `summaries` (F4/F5/T4) and `videos` (T3), no backfill, no RLS change, same idempotent-migration pattern already used twice for `model` and `resolved_via`. All four parts land in one migration; T4 is the only one that touches the endpoint rather than a single service, and it adds a counter, not a decision — nothing in the generation path branches on it. The only part that is more than bookkeeping is T3's optional reuse-on-regeneration path, which changes generation behaviour — it is listed as an open question and can ship as store-only first. **Provenance:** these were deferred to S-01 by the F-02 Phase 4 impl-review (`context/changes/transcript-llm-probe/reviews/impl-review-phase-4.md` F4 `:57-65`, F5 `:67-75`) but were **not carried into S-01's plan** — S-01 reasoned about latency and cost only as things to *bound* (the `HARD_MAX_TRANSCRIPT_CHARS` → 413 cap), never to *record*. The omission was found 2026-07-20, after S-01 phases 1–7 landed; verified absent from `src/`, `supabase/migrations/` and S-01's plan. Sequenced after S-01 rather than folded into it so the deploy-gated Phase 8 contract migration is not disturbed.
- **Scope notes:**
  - **F4 (latency):** additive `generation_ms integer` (or split `transcript_ms`/`llm_ms`) on `summaries`; thread timing through the persistence service. Motivation: the live F-02 run measured 33 s (inline transcript + LLM) vs. 254 s (async-job poll to exhaustion) — a wide, meaningful spread that is currently unrecorded.
  - **T3 (transcript persistence):** additive nullable `transcript text` + `transcript_fetched_at timestamptz` on **`videos`**, not `summaries` — a video carries one transcript but can have two summaries (one per character; the local DB already has such a pair for `dQw4w9WgXcQ`), so `summaries` would duplicate the text per character. Input size then comes free as `length(transcript)`, directly comparable to `LONG_TRANSCRIPT_CHARS`/`HARD_MAX_TRANSCRIPT_CHARS` (`src/lib/services/summaries.ts:84-85`), which are also char-based. **Motivation (measured 2026-07-20):** the S-01 F1 triage asked how output length compares to input and the question was unanswerable — `summaries` records `content` but nothing about the input. Output measured ~4.2–4.9k chars across 4 rows and is effectively constant in cost (~1.8 ¢/summary at Sonnet 5 intro rates), while input spans ~50× and dominates the bill; without the transcript, the ratio that matters cannot be computed. **Secondary win:** closes S-01's explicitly accepted "double transcript fetch on confirm" tradeoff (plan.md §Critical Implementation Details) — the 409 → "Generate anyway" resubmit currently re-fetches, occasionally re-triggering a paid Whisper job. **Erasure:** no new GDPR work — `videos.user_id` already carries `on delete cascade` to `auth.users` (`20260613145120_videos_and_summaries.sql:6`), so S-04 account deletion removes transcripts with the rest. RLS: reuse the existing per-user `videos` policies; the new columns need no separate policy. **Sizing:** bounded by `HARD_MAX_TRANSCRIPT_CHARS` at 200k chars/row worst case — negligible at MVP scale, worth revisiting only if the user cap lifts.
  - **F5 (cost):** add `usage: { include: true }` to the model options in `getSummaryModel` (`src/lib/services/llm.ts:7-9`, currently no options object), return `providerMetadata?.openrouter?.usage` from `summarize()`, persist to an additive `cost_usd numeric`. Feasibility already confirmed against `@openrouter/ai-sdk-provider` via Context7 — no new dependency. `cost` is `number | undefined`, so persist null-safely.
  - **T4 (Supadata spend — added 2026-07-27):** F5 covers only the OpenRouter half of the bill. The *other* paid provider is currently unmeasured, and since S-08 it is the one with two call sites per generation. Persist how many Supadata API calls a generation made and what they cost in credits — additive `supadata_calls integer` + `supadata_credits integer` on `summaries` (placement is the open question above). **Why it isn't just F5 again:** Supadata's response body carries no cost field, so credits have to be attributed by *operation type*, from the price table already captured in `context/changes/persist-video-metadata/docs/supadata-transcript.md` §Pricing + `supadata-metadata.md` §Pricing — metadata **1 credit flat**, native transcript **1**, generated (Whisper) **2 credits per minute of video**, a `206 transcript-unavailable` **1** (billable), job polling **free**. So a call count alone is not a cost: one `job`-resolved call can be worth 100 metadata calls. Record **both** — the count is the raw fact the user asked for and is exact; the credit figure is a derived estimate and should be commented as such.
    - **Attribution the code already supports:** `summaries.resolved_via` ('inline' | 'job', `20260709120000_add_resolved_via_to_summaries.sql:9`) distinguishes the cheap path from the Whisper path, and S-08 added `videos.duration_seconds` (`20260725120000_video_metadata.sql:28`) — the exact minute count Whisper is billed on. `inline` → 1 credit; `job` → `2 × ceil(duration_seconds / 60)`. Both inputs are already persisted, so a **retrospective estimate over existing rows is possible with zero new plumbing** and is worth running first, before any migration, to size the problem.
    - **Call sites to count** (all in the generate request): `fetchTranscript` — 1 billable call, plus up to 12 *free* `getJobStatus` polls (`src/lib/services/transcript.ts:100-102`, do not count these as spend, but counting them separately is diagnostic — they measure Whisper latency); `fetchVideoMetadata` — 1 call, **plus a second one on the retry path** (`src/lib/services/metadata.ts:146-149`), which is real spend the naive "1 per generation" assumption misses; and the quote-cache hit path, which spends **zero** and must not be counted as one (`getTranscriptQuote`, `src/lib/services/transcript-guard.ts:67`). Threading a small mutable counter through the endpoint is enough — no new abstraction.
    - **Free ground-truth check:** `GET /v1/me` returns `usedCredits` / `maxCredits` and is free to call (`docs/supadata-account-limits.md:9`). Measured 2026-07-25: `maxCredits: 100`, `usedCredits: 29`. This defuses the original objection recorded below that C "protects the budget by breaking the product for everyone". (2) The budget figure comes from **`GET /v1/me` refreshed lazily** (stored row, TTL in minutes, refreshed in-line by the request that needs it) **plus a ledger delta since that reading** — neither source suffices alone: `/v1/me` is authoritative but is an HTTP call that would land directly before the transcript fetch and break the 1 req/s spacing `generate.ts:552-556` maintains, while `supadata_calls` is free and instant but does not know when the vendor's billing period resets, so a purely ledger-derived total drifts out of phase. ### S-10: Screen the transcript for injection before it reaches the LLM

- **Outcome:** (guardrail) a transcript is checked for injection attempts before it is sent to the model, and a transcript that fails the check — or that cannot be checked — is not sent at all. The user is told the video could not be summarized rather than receiving a summary shaped by the video's author instead of by the app.
- **Change ID:** transcript-injection-guardrail
- **PRD refs:** — (no direct PRD ref; roadmap-originated integrity guardrail, sibling of S-05's OpenRouter-side and S-09's Supadata-side cost guards — this one guards the *prompt boundary* rather than spend)
- **Prerequisites:** S-01. **Sequence after S-09** — see below.
- **Parallel with:** S-02, S-03
- **Blockers:** —

**Decisions already made (user, 2026-07-31) — these are settled inputs to planning, not open questions:**

1. **Injection only — the app does NOT screen subject matter.** YouTube already moderates what it hosts, so re-adjudicating the topic of a video would duplicate someone else's moderation with worse information, and would contradict the product's premise: summarizing a video *about* a difficult subject is exactly the watch/skip decision the app exists to serve. What has no legitimate reading is a transcript that tries to *steer the model*. That, and only that, is the target.
2. **Fail-closed.** If the check cannot produce a verdict — screen unavailable, timed out, errored, unparseable — the generation is refused. Unchecked content does not reach the LLM. This is the deliberate choice of the stricter side: availability of the summarization flow yields to the guarantee that nothing unscreened is forwarded.

- **What fail-closed commits the plan to** (consequences to design for, not arguments to revisit):
  - **A real verdict-producing check is now part of the slice.** Fail-closed is a rule about what to do when a check fails, so there has to be a check that can pass or fail. Prompt-level hardening (delimiting the transcript, telling the model the material is data and not instructions) produces no verdict and therefore cannot satisfy this on its own — it is worth doing as defence-in-depth, but it is not the deliverable.
  - **Two different refusals, two different messages.** "We checked this and refused it" and "we could not check it" are not the same event and must not share user-facing copy — the second is an outage the operator needs to see and the user should be invited to retry, the first is not.
  - **A refusal must not cost the user a credit.** The app already has pre-debit exit paths that refuse without spending; the screen belongs on that side of the debit so no refund path is needed. Note the Supadata transcript credit is unavoidably already spent by screening time — that operator-side cost on an outage is the accepted price of fail-closed.
  - **Precision matters more than it would under fail-open**, because a false positive now blocks generation outright. The refusal rate needs to be visible to the operator; a guard nobody can measure cannot be shown to be calibrated. S-07's ledger is the precedent for how this project records that kind of fact.
- **Deliberately not specified here: the mechanism and its placement.** Local heuristics vs. a small screening model vs. something else, where exactly the check sits in the request, whether a verdict is cached per video, and what it costs in latency and money — all deferred to planning. **This deferral rested on S-09 restructuring the pre-LLM pipeline — and that premise is now void (2026-07-31).** S-09 chose lever A over the duration pre-gate, so the metadata call does not move and the pre-debit gate order is unchanged; the "details with a known expiry date" argument no longer applies. **The `plan after S-09` sequencing is left standing anyway, but on a weaker and different footing:** S-09 still adds a breaker and a cache lookup to the same pre-debit stretch, and treating the two as one sequence of pre-LLM gates remains the better design. That is now a preference, not a blocker — revisit if S-10 becomes urgent, since planning them in parallel is no longer unsafe.
- **Risk:** The defect is structural and present today — the transcript is passed to the model in the position the model treats as the user's own request, with the app's instructions carried separately, so caption text competes with app instructions on equal footing. Fail-closed raises the stakes of the implementation relative to a permissive guard: the check becomes a hard dependency of the core paid flow, so its reliability, its timeout budget and its false-positive rate are all load-bearing rather than best-effort. That is the main thing planning has to get right, and the main reason not to reach for a heavyweight mechanism first. Cost and latency are real but secondary — per-summary spend is already measured (S-07), so the overhead of a screen is quantifiable before it ships rather than after.
- **Not in scope:** screening subject matter (decision 1); moderating the *summary output*; user-reporting or appeal flows; per-user trust or rate models.
- **Status:** proposed

### S-14: User marks a summary as worth / not worth watching (MAR-25)

- **Outcome:** on each saved summary the user records their watch/skip decision with a two-option toggle — "worth watching" or "not worth watching". The options are mutually exclusive, clicking the active option clears it, and a new summary starts unmarked. The mark is saved, so it survives a reload and shows up wherever the summary is listed.
- **Change ID:** summary-watch-verdict
- **Linear:** MAR-25
- **PRD refs:** — (no direct PRD ref; roadmap-originated, raised by the user 2026-09-14). It records the decision the product exists to serve (§Vision recap: *"on the basis of which the user decides whether to watch or skip it"*). **Second motive, stated openly:** this is the first user-initiated **Update** on a persisted summary. S-03's Risk note says delete "closes the CRUD on summaries", but it doesn't — `20260731130000_summaries_single_writer.sql:31` grants `authenticated` only `select, delete`, so the app has Create/Read/Delete and no Update. The 10xBuilder MVP check (2026-09-14) flagged exactly this gap.
- **Prerequisites:** S-02 (the list and card this toggle lives on)
- **Parallel with:** S-10, S-11, S-12 — none of them touch the summary card's persisted state or the `summaries` grants
- **Blockers:** —

**Decisions already made (user, 2026-09-14) — settled inputs to planning:**

1. **Three states, not two.** `null` (unmarked, the starting state) · `true` (worth watching) · `false` (not worth watching). A plain checkbox has two states and can't get back to "unmarked", so it's rejected.
2. **Mutually exclusive and clearable.** Choosing one option deselects the other, and clicking the active option returns the summary to `null`. That's the shape of a single-select toggle group with deselection allowed (shadcn `ToggleGroup type="single"`), not two independent checkboxes.

- **Scope notes:**
  - **Schema:** one additive nullable column, e.g. `summaries.worth_watching boolean` (default `null`, no backfill), in one idempotent migration.
  - **Privilege — column-scoped, not table-wide.** `grant update (worth_watching) on public.summaries to authenticated;` — **not** `grant update on public.summaries`. The single-writer migration exists so the service-role `persist_summary` RPC is the only writer of `content`, `reservation_id` and the cost/telemetry columns. A table-wide grant would let a client rewrite a paid summary's content or detach it from its reservation. Confirm the owner-scoped `for update … using (auth.uid() = user_id) with check (auth.uid() = user_id)` policy from `20260613145120_videos_and_summaries.sql:59` is still in place, and re-create it if a later migration dropped it.
  - **Endpoint:** `PATCH /api/summaries/[id]` next to the existing `DELETE` in `src/pages/api/summaries/[id].ts`, following its shape: `401` unauthenticated, then zod on the id (`z.uuid()`) and body (`worth_watching: z.boolean().nullable()`), then the anon SSR client (never `createAdminClient`, because RLS is the enforcement point), then `404` for zero rows and a masked `500`. CSRF is covered by Astro's `checkOrigin`, as for `DELETE`.
  - **Service:** `src/lib/services/summary-update.ts` with an injected client, mirroring `summary-delete.ts`. No `user_id` filter, for the same reason.
  - **Read path:** `listSummaries` (`src/lib/services/summary-list.ts`) must select the new column, or the mark vanishes on reload. That would be a transient UI edit, which is exactly what doesn't count as Update.
  - **UI:** the toggle on the summary card, with an optimistic update and rollback on failure. Copy goes through `src/lib/copy/pl.ts`.
  - **Not touched:** the paid path, credits, the Supadata budget and `persist_summary`. Setting a mark is free and never a generation.
- **Tests (per `test-plan.md` §6.1–§6.3):**
  - A hermetic unit test for the service (`stubReturning` / `stubFailing`): one row updated → `true`, zero rows → `false`, an error propagates.
  - **Risk #4:** a case in `src/test/cross-account-policy.int.test.ts` — account B updating account A's summary by id changes nothing, and A's value is unchanged when read back through A's own session.
  - A column-privilege probe: an authenticated client trying to update `content` (or `reservation_id`) on its **own** row is refused. This is the regression a table-wide grant would introduce.
  - Update the grant roster in `src/test/authorization-invariants.int.test.ts`, which will otherwise fail on the new `update` privilege — by design.
- **Unknowns:**
  - Should the list's client-side filter gain a worth / not worth / unmarked facet? — Owner: user. Block: no (can ship without it).
  - Does the mark feed Open Roadmap Question 1 (the 75% "good enough" criterion)? — Owner: user. Block: no. **It should not be read as a quality signal by default:** "not worth watching" judges the *video*, and a summary that correctly talks the user out of a bad video is a *good* summary. At most a weak proxy; a real quality measure stays T-5's job.
- **Risk:** Low implementation risk — one column, one route, one card control, and the route and service have a direct precedent in S-03. The one real care point is the **privilege shape**: the easy migration (`grant update on public.summaries`) quietly undoes the single-writer guarantee on paid content, and nothing in the UI would show it. That's why the column-scoped grant and its probe test belong in the slice, not in a follow-up. Priority is higher than its size suggests, because it clears the last unmet 10xBuilder technical criterion.
- **Status:** proposed
